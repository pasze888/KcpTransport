# 规格：客户端 KCP 连接（地址前缀 opt-in）

状态：ready-for-agent（tracker = GitHub Issues，见文末链接）
依赖决策：ADR-0001 内嵌源码、ADR-0002 零适配层、ADR-0003 前缀 opt-in
词汇：本规格使用 KcpTransport/GLOSSARY.md 的语言（字节流通道／双栈监听／地址前缀／前缀剥离／会话号／单帧上限／快速失败／静默关闭／内嵌）

## Problem Statement

玩家想让游戏连接跑在 KCP(UDP) 上以获得弱网下的低延迟，但今天只有服务端能听 KCP，客户端进服永远走 TCP——装了模组的玩家无论服务器是否支持 KCP，都拿不到任何收益。同时，未装模组的 vanilla 玩家和 Realms、服务器转送等路径必须完全不受影响。

## Solution

玩家在服务器地址里写地址前缀 `kcp;host:port`，客户端便在这条连接上用 KCP 承载字节流通道，其上的原版包管道一行不改；不写前缀则一切照旧走 TCP。前缀是玩家的显式决定，因此没有自动协商、没有探测超时、没有回退、没有每主机记忆：写了前缀而对端没监听，结果就是连接失败（快速失败）。服务器侧维持双栈监听，vanilla 客户端照常进服。

## User Stories

1. 作为装了模组的玩家，我想在服务器地址里写 `kcp;` 前缀，以便对某一台服务器显式启用 KCP。
2. 作为装了模组的玩家，我想让不带前缀的地址保持完全原样的 TCP 行为，以便我不写前缀时模组对我毫无影响。
3. 作为装了模组的玩家，我想在服务器列表里看到带前缀的条目能正常显示 motd 和延迟（前缀被剥掉后 ping 走 TCP），以便启用 KCP 不会让条目变成 Unknown host。
4. 作为装了模组的玩家，我想让进服连接在写入前缀后真的建立在 UDP 上，以便弱网/丢包环境下的卡顿减少。
5. 作为装了模组的玩家，我想在写前缀但对端没有 KCP 监听时看到明确的连接失败，以便我知道是配置错了而不是模组坏了。
6. 作为装了模组的玩家，我想让失败等待时间与原版 TCP 连接失败同级（原版同款读超时），并且可用系统属性调短，以便调试时不必等满。
7. 作为未装模组的 vanilla 玩家，我想照常通过 TCP 进入装了模组的服务器，以便服务器的 KCP 能力对我完全透明。
8. 作为服务器管理员，我想让服务器同时双栈监听 TCP 与 UDP 同一端口号，以便我不必再开第二个端口或改防火墙端口表。
9. 作为服务器管理员，我想在 UDP 绑定失败时只看到一条警告而服务照常运行，以便启用 KCP 不会让服务器起不来。
10. 作为服务器管理员，我想让 KCP 会话随服务器关闭与 LAN 开关一起被回收，以便不必担心残留监听。
11. 作为服务器管理员，我想让端口扫描/监控探活发到 UDP 端口的垃圾包不会打断任何活会话，以便上游那个坏包致命的问题不在我的服上复现（静默关闭）。
12. 作为服务器管理员，我想让 UDP 断线被当作正常会话结束而不是错误，以便日志不被 KcpException 噪音淹没。
13. 作为压测操作者，我想用系统属性调 KCP 的 nodelay/interval/fast-resend/nocwnd/MTU/发送窗/接收窗，以便扫描参数而不必改代码重编译。
14. 作为压测操作者，我想在同一份冒烟框架里得到超大帧卡住的实机数字（发送窗/远端窗/重传计数停在哪一步），以便决定要不要动窗口而不是靠猜。
15. 作为玩家，我想知道单帧上限：超过上限的大包会被直接拒绝而不是排队，以便我对某些模组的超大 chunk 包有预期。
16. 作为 Realms 玩家，我想让 Realms 连接始终走 TCP，以便我不需要为它写前缀也不会意外失败。
17. 作为被服务器转送的玩家，我想让 transfer 后的重连走 TCP，以便转送目标是否支持 KCP 的不确定性不会影响我。
18. 作为用 QuickPlay/直连命令进服的玩家，我想让这些路径同样识别地址前缀，以便我的启用方式在所有入口一致。
19. 作为模组维护者，我想让内嵌代码的每一处分叉都能被一次 grep 找全，以便重新内嵌上游新版本时不靠记忆对账。
20. 作为模组维护者，我想让第三方出处在提交信息与文件头都写明，以便搬运外部代码的合规要求被满足。
21. 作为未来的读者，我想在 ADR 里看到「为什么不做自动协商」以及被否决的方案，以便没人再来把回退逻辑「修」进去。
22. 作为未来的读者，我想在词汇表里看到「双栈监听」在 KCP 仓与 IPv4/IPv6 语境下的区别，以便不混用术语。
23. 作为 CI 的消费者，我想让冒烟测试挂在标准校验任务里，以便一次绿勾就证明 KCP 接线可用而不仅仅是编译过。
24. 作为发布流程的消费者，我想让 jar 名与发布标签同构、版本坐标的真源保持 gradle.properties 不变，以便新增功能不打乱既有发布链路。
25. 作为分发者，我想让模组许可证与内嵌的 MIT 源码自洽，以便发布到模组托管平台时不会被质疑合规。

## Implementation Decisions

**只在字节流通道这一层替换。** 其上原版管道（分帧、流控、编解码、压缩、加密、Connection）逐字节复用，已由实测证明不需要任何消息→字节流适配层（ADR-0002）。新增的客户端接线必须与既有服务端接线共用同一份管道配置逻辑，避免两条路径各维护一份管道——这也是架构评审候选 A 的结论：抽出一个深模块负责「把原版序列化栈与 Connection 挂到任意字节流通道上」，服务端与客户端各留一个薄适配调用它。冒烟测试必须调用这份共享模块，否则它测的不是真接线。

**启用机制＝地址前缀，意图载体＝前缀剥离点。**（ADR-0003）解析与剥离发生在地址被送去 DNS 解析之前，因为解析之后意图再无载体。前缀语法只有分号式可用（带协议的写法会被 Guava 的 HostAndPort 判成端口号而整串解析失败）。传递形态采用上游 raknetify 已被验证的两段式：在连接线程对象的构造点解析前缀、把「这条连接走 KCP」记为该实例的字段，并就地重写它捕获的地址对象为剥掉前缀的干净地址；随后在连接方法内包裹原版 bootstrap 调用，依据实例字段决定用 KCP 通道还是原样走 TCP。刻意不使用静态登记表：登记表的键是主机名或地址，而连接真正拿到的是解析后的 IP，键会静默对不上——三家上游无一使用此法。

**不做的事都是决策。** 无自动协商、无探测超时、无回退、无每主机持久化记忆。Realms、服务器转送、QuickPlay 之外的一切非前缀路径保持 TCP；列表状态 ping 只剥前缀、不换传输（QUICify 同款取舍）。

**失败语义＝快速失败。** 原版同款读超时兜底，超时秒数走系统属性可调。内网场景下 ICMP 端口不可达会几乎即时回弹（本机探针实测 1ms），公网黑洞则等满超时；后者是接受的代价，不引入回退去掩盖。

**参数全部走系统属性**，含五个 UKCP 旋钮与发送窗/接收窗，不引入配置 API、不写配置文件、不加总开关（前缀本身就是开关）。默认值维持现值。

**单帧上限先记录后处理。** 单帧所需段数超过接收窗常数时会被发送函数直接拒绝而非排队；本期只在 README 与词汇表写明该上限，不实现按尺寸切分/丢弃——调研结论是没有任何上游做过，且机制尚未量清。

**大帧诊断排在客户端接线之前**（本期第一个动作）。在同一份冒烟框架里观察超大帧的发送缓冲、远端窗、重传计数停滞在哪一步，产出实机数字后再决定是否调窗口参数；在此之前不动 vendored 层。

**vendored 层的行为分叉保持现状**：死链静默关闭、坏包丢弃，两处已记入第三方声明文档的「Behaviour changes」；重新内嵌时按 marker 对账（架构评审候选 C：每处分叉加可 grep 的单行 marker，并删掉搬运残留的孤儿类）。

**许可证改为 MIT**，与内嵌源码一致；第三方声明文档保留并继续列上游版权人。发布链路沿用既有约定（版本坐标真源 gradle.properties、标签整串对账、jar 名同构、发布说明取自变更日志），本期不动 release.yml。

## Testing Decisions

好测试只断言外部行为：给定输入的连接配置，产出的是不是能在 KCP 上把原版协议跑通的通道；不断言内部字段、不断言注入器细节、不测「有没有调用某个私有方法」。

**测试接缝沿用既有的那一个，不新增框架。** 即仓库里独立于主源集的冒烟源集＋其 Gradle 运行任务（已挂进标准校验任务，带超时护栏）。它是最高可用的接缝：进程内同时起真实 KCP 服务端监听与客户端通道，并且已经能把 MC 真实的分帧/流控/封装类挂上通道跑。本期在它之上加三类断言：

1. **前缀解析的纯函数行为**：带前缀／不带前缀／带端口／只有主机／畸形写法，各自得到什么启用标志与干净主机串。这是本期唯一的全新逻辑，必须被直接覆盖。
2. **正向接线**：客户端走共享管道配置模块连上真实双栈服务端，完整往返一个 MC 握手包（不是自造帧），从而证明「真接线」而非「仿制接线」；同时断言同端口号上 TCP 仍能独立握手成功，即双栈互不干扰。
3. **失败语义**：对没有 KCP 监听的地址发起 KCP 连接，断言在超时护栏内以失败收场而非挂死，并且同地址的 TCP 路径不受影响。

超大帧的诊断以观测形式加在同一框架里（打印窗口/重传计数），不作为断言——机制未定之前不能把未证实的行为写成通过的测试；机制查清后改为断言单帧上限的真实表现。

**不测什么**：注入器是否命中、Minecraft 客户端界面里的地址编辑流程、真实登录进服。这些属于实机验证：起服务器与客户端各一次，用带前缀地址进服，看调试面板网络列确认走的是 UDP——按既有验证纪律，实机数字才算数。NeoForge GameTest 不引入（它起不出对照的传输环境，YAGNI）。

**既有先例**：当前冒烟程序已经覆盖 Netty 版本断言、每客户端独立非零会话号、两个客户端不串话、垃圾包不打断活会话、超大帧逐字节相等。本期新增用例沿用同一风格：单个 main、显式断言、失败即抛、打印可读进度、由任务超时护栏兜底。

## Out of Scope

- 状态 ping 公告式的自动协商（QUICify/NetBridge 形态）——二期候选，本期不做。
- 探测超时、失败回退 TCP、每主机能力的持久化或内存缓存。
- 列表 ping 走 KCP 及把 KCP 往返时延塞回列表延迟显示。
- Realms、服务器转送、QuickPlay 等非前缀路径的 KCP 化。
- 超大包的按尺寸切分或丢弃策略；窗口参数的最终调优（等诊断数字）。
- 面向玩家的配置界面/配置文件/模组总开关。
- FEC/纠删码、多流优先级（上游只有 NetBridge 用 Rust 侧做 FEC，QUICify 的多流优先级依赖 KCP 没有的流语义，抄不了）。
- release.yml 发布流水线、变更日志与 README 重写（README 本期只补前缀用法与单帧上限两条）。
- 架构评审候选 D 之外的重构；vendored 层那七千余行不做门面封装。
